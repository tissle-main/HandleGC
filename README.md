# HandleGC

## SIP OS
Inspired by: [Singularity OS](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/osr2007_rethinkingsoftwarestack.pdf)

SIP OS (Software Isolated Processes Operating System) - операційна система, процеси якої ізолюються програмно.
Звичайні операційні системи мають апаратну ізоляцію процесів (HIP). Досягається це завдяки маніпуляціям із page table (так званий context switching),
який дозволяє створити для кожного процесу імітацію доступності всієї віртуальної пам'яті. SIP операційні системи такого механізму не мають,
тому всі процеси будуть знаходитись в межах однієї віртуальної пам'яті. Так само було для OS при 16-розрядних процесорах, коли віртуальної пам'яті тоді не було,
і всі процеси працювали напряму із фізичною пам'яттю.

Програмна ізоляція для SIP OS досягається завдяки мові програмування, яка просто не буде мати інструментів для маніпуляції із адресами, та відповідно компілятором.
Однак, якщо усі процеси будуть ділити віртуальну пам'ять, можуть виникати проблеми із фрагментацією та її синхронізацією.
Дану проблему може вирішити Garbage Collector (GC). Однак звичайні GC люблять зупиняти роботу програм, коли вони починають працювати.
Для операційних систем - це недопустимо. Тому нам потрібне в ідеалі повністю concurrent рішення.

## OS GC
Звичайний GC має 3 фази, при яких відбувається зупинка всієї програми: "Mark and Sweep" -> "Compact" -> "Reference Recovery".
Спочатку будується повноцінний граф об'єктів та операції при видаленні об'єкта, далі відбувається переміщення живих об'єктів, після чого - відновлення посилань.
"Mark and Sweep" потребує інформації про кореневі об'єкти (стек, регістри), що вимагає багато метаданих.
"Compact" вимагає великих вільних областей пам'яті (бо переміщення об'єктів відбувається за межі самої кучі).
"Reference Recovery" так само потребує граф живих об'єктів, а також інформацію про те, де знаходяться посилання.
Всі ці фактори роблять GC громіздким та складним. Однак можна спробувати все спростити.

"Mark and Sweep" відповідає за автоматичне видалення об'єктів, до яких більше немає активних посилань (тобто немає доступу до об'єктів із кореневих об'єктів).
Вирішення даної проблеми пропонує мова "Rust", своєю ownership системою. Є пропозиція передати відповідальність за lifecycle об'єктів на плечі мови та компілятора.
Тоді фаза "Mark and Sweep" зникає із GC. Мова та компілятор очевидно повинні бути власні, але вони повинні мати ownership механізм посилань.

"Reference Recovery" потребує інформацію про те, де знаходяться посилання, що ускладнить GC та потребуватиме додаткових ресурсів для відновлення посилань.
Щоб позбутись цієї фази, нам потрібно зробити посилання сталими, але при цьому дозволити переміщення об'єктів.
Такі обмеження може задовільнити окремий сталий handle, який буде тримати актуальне посилання на об'єкт.
Тоді фаза "Reference Recovery" зводиться до простого оновлення єдиного посилання, що може стати частиною "Compact".

При "Compact" для звичайних GC, всі живі об'єкти переміщуються в іншу частину пам'яті. Для SIP OS, де буде одна віртуальна пам'ять для всіх процесів,
такий варіант не підходить, тому переміщення об'єктів буде відбуватись в межах самої кучі (так як це візуально зазвичай і представляється).
При цьому, усю фазу можна зробити повністю concurrent (handle дуже в цьому допомагає).

В результаті отримуємо GC, який фактично має одну concurrent "Compact" фазу. Звичайно це дається не за безплатно.

## Memory Context
64-розрядні процесори підтримують адресацію не всієї віртуальної пам'яті, через обмеження page table. Реальна величина адресів == 48 та 57 біт (6 та 7.1 байтів).
Ця особливість ділить віртуальну пам'ять на 3 частини [простір нижніх адресів|неканонічні адреси|простір верхніх адресів].
В звичайних операційних системах нижні адреси призначені для user-space, а верхні - для kernel-space.
Однак для SIP OS, разом із GC, віртуальну пам'ять можна поділити так:
```
Нижній адресний простір (GC Heap): [GlobalHeap -> | FreeSpace | <- AllocationHeap]
Верхній адресний простір (Other): [Globals | HandleTableBitmap | HandleTable | UnmanagedHeap]
```
Нижній адресний простір повністю віддається для GC (Managed Heap), а верхній залишається для всього решта (Unmanaged Heap).
Кожна частина просторів описана нижче. Важливо, що тут поки що не враховано зарезервовану пам'ять та пам'ять, яка потрібна для різних апаратних модулів.

## Execution Context
Кожен процес має власні програмні потоки. Це окремий стек + викликаний метод (який в собі викликає інші методи і т.д.). Кожен потік виконується паралельно,
однак не завжди одночасно (їх може бути дуже багато). За виконання потоків беруться логічні процесори (або їх можна назвати апаратні потоки).
Логічний процесор - це ядро (або пів ядра), яке саме виконує команди. Одночасно їх існує в кількості, яка == кількості ядер (x2).
Відповідно періодично кожен апаратний потік бере програмний потік та його виконує. Зміна потоків вимагає тільки збереження усіх регістрів в стек,
вибір нового потоку та завантаження усіх регістрів із стеку цього потоку, що займає невелику кількість часу. Context switching потребує значно більше часу.
В SIP OS кожен процес немає фізичного представлення, тому існує тільки великий список програмних потоків.

Хоч стек для кожного програмного потоку буде власний, однак завдяки спільній пам'яті (і відповідно кучі), алокатори також можуть бути спільні.
Щоб уникнути постійної синхронізації алокації об'єктів, кожен апаратний потік буде мати власний алокатор (фактично окреме місце для розміщення нових об'єктів).

Доступ до об'єктів буде відбуватись через handle, тому щоб не отримати ситуацію, коли потік зупинив свою роботу в непотрібний момент,
в коді компілятор буде розміщувати SafePoints - місця, де стан системи буде безпечний, а потік буде вирішувати подальші дії.

## Algorithms and Structs
### GC Heap
Об'єкт в кучі буде мати структуру [ObjectHeader | Data],
де ObjectHeader має структуру [Alive (1 біт) | TypeAddress (63 біти) | Length (32 біти) | HandleIndex (32 біти)]. Разом 16 байтів.
Alive показує чи об'єкт ще живий. TypeAddress буде мати адресу знаходження метаданих типу (фактично він також буде ідентифікатором типу даних).
Length - довжина об'єкту разом із ObjectHeader. HandleIndex - індекс відповідного handle в HandleTable.

Об'єкти в кучі розміщуються один за одним без вільних проміжків.
GC при очищенні кучі проходиться зліва направо по кожному об'єкту, переміщуючи живі об'єкти справа наліво, поверх неживих.

### GlobalHeap & AllocationHeap
Якщо використовувати GenerationHeap, яка існує в .NET GC (коли нові об'єкти розміщуються наверху кучі), в нас виникне проблема переміщення та алокації нових об'єктів.
Ідею GenerationHeap залишити потрібно, бо це вирішує проблему синхронізації алокаторів. Хорошою ідеєю є розділення вже алокованих об'єктів та нових.
Відповідно так з'являється дві кучі "GlobalHeap" та "AllocationHeap". GlobalHeap містить усі старі живі об'єкти,
тоді як AllocationHeap складається із окремих регіонів пам'яті. Кожен апаратний потік бронює регіон та розміщує там об'єкти послідовно.
Коли регіон заповнюється, апаратний потік бере вільний регіон. Тоді пізніше GC може взяти заповнений регіон та перемістити звідти усі живі об'єкти в GlobalHeap,
таким чином звільнивши його для повторного використання. GlobalHeap GC може очищувати собі незалежно.

### HandleTable
HandleTable - область пам'яті, де будуть розміщуватись handle. Кожен handle довжиною 8 байт. Як і з AllocationHeap, в нас виникає проблема із синхронізацією,
тому вся таблиця ділиться на частини (Chunks), по 64 handle кожен. Кожен апаратний потік бере собі chunk. Після заповнення chunk, потік вибирає новий вільний.
Щоб позначити вільні/зайняті chunk, використовується HandleTableBitmap, де кожен біт відповідає за 1 chunk.
GC періодично перевіряє зайняті chunks на наявні вільні handle, та відповідно синхронізує HandleTableBitmap.

### Object Allocation
Алокація нового об'єкта потребує резервування місця в AllocationHeap + отримання вільного handle.

### Handle Sync
Структура handle: [RSFlag (1 біт) | GCLocked (1 біт) | UsageCount (15/6 біт) | Address (47/56 біт)]. Разом 8 байт.
Адреси, які може містити handle завжди будуть знаходитись в нижній частині адресного простору, тому останній біт нам не потрібен.
Особливість handle в тому, що нам потрібно синхронізувати доступ до об'єкта при роботі GC. Це можливо зробити тільки через атомарний лічильник,
бо із об'єктом одночасно може працювати кілька апаратних потоків. Однак, щоб не втрачати продуктивність, нам потрібно зменшити час синхронізації до мінімуму.
RSFlag (Require Sync) буде вказувати на те, чи GC планує перемістити об'єкт. Якщо GC не працює - синхронізації не потрібно,
тому доступ до об'єкта зводиться до занулення усіх бітів, окрім Address + потрібне зміщення. При RSFlag, спочатку потрібно перевірити чи GCLocked не встановлений,
як ні - атомарно збільшити UsageCount і вже тоді отримати потрібну адресу. Після використання потрібно UsageCount атомарно зменшити.
GCLocked встановлює GC, перед тим, як перемістити об'єкт. Якщо GCLocked встановлений, потоки повинні чекати, поки об'єкт не переміститься.
В цей час GC чекає, поки UsageCount стане 0 - тобто об'єкт більше не буде використовуватись. Тоді об'єкт переміщується,
замінюється адреса в handle та синхронізація об'єкта зупиняється - потоки можуть далі використовувати fast-path.
Щоб точно бути впевненим, що апаратні потоки не використовують fast-path, коли RSFlag встановлений в 1, GC після цього моменту очікує,
поки усі апаратні потоки не дійдуть до SafePoint. Це гарантія того, що fast-path більше не використовується. Це збільшує час переміщення об'єкту,
тому RSFlag GC встановлює для групи об'єктів, які він збирається перемістити.

### GC Important
GC може виконувати очищення паралельно (тільки GlobalHeap або тільки AllocationHeap) або (HandleTableBitmap). При цьому це може робити будь-який апаратний потік,
а також це може бути частинами (особливо актуально для 4- апаратних потоків).

### Unmanaged Heap
Некерована куча буде містити об'єкти, які переміщуватись не будуть. При цьому виділення пам'яті в ній буде відбуватись сторінками пам'яті (кратно 4096 байт),
тому вона актуальна для великих об'єктів. Кожен виділений блок пам'яті буде мати свій MemoryBlockHeader.
Його структура [CurrentAlive (1 біт) | CurrentLength (63 біт) | PreviousAlive (1 біт) | PreviousLength (63 біт)]. Разом 16-байт.
Інформація про попередні блоки потрібна, щоб об'єднювати послідовно кілька вільних блоків пам'яті. Дана куча потребуватиме синхронізації.
